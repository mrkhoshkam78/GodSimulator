# v1.9 Final Report — Asset-Based Troop Pipeline

## Current rendering architecture
- Game loop: requestAnimationFrame in `Game.loop`
- Entities: Troop, Enemy, Castle, Weapon, Projectile
- Combat: CombatSystem + WaveSystem unchanged
- **New:** AssetManager → TroopVisual → Canvas drawImage of PNG frames

## Previous troop rendering
- 100% runtime Canvas primitives (arc/ellipse/fillRect) in Troop.js
- No image files under assets/

## New rendering method
1. PNG frames on disk under `assets/troops/swordsman/{idle,walk,attack,hit,death,special}/`
2. `metadata.json` describes frame lists, duration, loop, hitFrame, origin
3. `AssetManager` loads/caches images + metadata (preload at game start)
4. `TroopVisual` owns animation state/frame timing/facing/shadow
5. `Troop` gameplay entity attaches visual when assets ready; combat logic unchanged
6. Attack damage synchronized to `hitFrame` in metadata

## New asset files
- 42+ PNG frames (idle 8, walk 8, attack 8, hit 4, death 8, special 6)
- Per-state spritesheets in `spritesheet/`
- `assets/troops/swordsman/metadata.json`

## Performance
- Images loaded once, cached in Map
- drawImage only; no image creation in game loop
- Multiple swordsmen share same cached Image objects

## Remaining work for other troops
1. Generate/import PNG sets into `assets/troops/<id>/` with same metadata schema
2. Add id to `AssetManager.preloadBattle([...])`
3. No Troop.js combat changes required — visual attaches by id when pack exists
4. Optional: replace procedurally generated PNGs with hand-painted/AI art drop-in

## Honesty note
Frame PNGs were **generated programmatically (PIL)** as real image files so the pipeline is genuine (load → cache → drawImage). For commercial paint quality, replace those PNGs in-place; code does not need changes.
